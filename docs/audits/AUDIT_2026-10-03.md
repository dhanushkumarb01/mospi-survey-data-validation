# MoSPI — Independent technical and methodological audit

Date: 3 October 2026 · Scope: the complete repository (`preprocessing/`, `peer_groups/`, `statistical/`, `contextual/`, `ml/`, `pattern/`, `fusion/` incl. UI), its design documents, and the real stored runs. Primary data examined: Calendar 2024 first visit (415,549 persons, 12,716 FSUs); cross-checks on 2023–24 and 2025 where relevant.

Reference documents: *Project Brief — NSO Survey Data Validation Software* (HSD/NSO/MoSPI) and *Intelligent Survey Data Validation Platform — Research Documentation v1.0*.

No algorithm, evidence layer or stored run was modified for this audit. Every number below was recomputed from the stored Parquet outputs with DuckDB queries (scratch scripts, not committed). The test suite passed (56 tests) before any change. Passing tests show the software behaves as coded; they say nothing about whether the method finds real errors.

Finding categories are kept separate throughout:

- **BUG** — the code does not do what it claims to do.
- **METHOD** — the code does what it claims, but the method is inappropriate or unsound for this purpose.
- **LIMITATION** — a defensible research or engineering choice that has not been scientifically validated.
- **SCOPE** — a requirement that has not been built.
- **PRESENTATION** — a wording or UI problem.

---

## 1. Headline assessment

The platform is a well-engineered, provenance-safe evidence pipeline with a careful human-in-the-loop review interface. It **does not yet solve the problem the brief describes**. The brief's central gap is:

> "there is no mechanism at present to the supervisors to use the past data or related survey data for checking anomalies and inconsistencies."

MoSPI compares every record only with other records **from the same survey round**. Nothing is learned from a previous round and applied to a new one. Temporal drift produced **0 assessable results**. The 2023–24 revisit (panel) evidence is computed but never reaches the review list. The current post-2025 design (2025 data) has no Fusion run, so it is absent from the UI. No detection-performance evaluation exists: there are no injected errors, no labels and no E0–E7 execution.

Several evidence components also have defects that change what supervisors see:

- The salaried-earnings model's "estimated typical value" is systematically about half the true typical value.
- FSU heaping statements state the wrong direction in about half of the earnings rows.
- FSU-level evidence pushes 1,974 individual records to top risk.
- Priority bands are an artefact of multiplying two percentile ranks.

What the system currently delivers is best described as **a within-round outlier-ranking and review-audit tool for PLFS first-visit person records**. It is not yet an intelligent validation platform using historical data.

## 3. Findings by severity

Each finding gives the location, evidence, category, what it affects and whether it should be fixed before a demonstration ("Demo").

### CRITICAL

**C1 — The conditional (gradient-boosted) earnings model is biased low; its "estimated typical value" is wrong and shown to supervisors.**
- *Location:* `ml/conditional_models.py:44-78`; `ml/config.py` (`conditional_max_iterations=30`); displayed by `fusion/explain.py::_ml_sections` and `_unusual_facts`.
- *Evidence:* the model is trained on **all** persons. 368,789 of 415,549 have salaried earnings `0`; this is the structural not-applicable value, not a reported zero. With `log1p` targets, 30 iterations at learning rate 0.08 cannot close the gap between the near-zero baseline and earners' log-earnings. At most 1−0.92³⁰ ≈ 92% of the gap is covered, leaving earners about 0.7 log points short.
  - For salaried earners the median *prediction ÷ peer median* is **0.474**, and **97.6%** of predictions fall below the peer median.
  - The mean log residual is positive in every state (+0.51 to +1.26).
  - **100%** of the model's top-1% flags have observed > predicted (median observed ₹64,000), so it re-flags high earners already caught by the statistical layer.
  - Real case #1: reported ₹2,45,000; peer middle half ₹15,000–30,000; UI "Estimated typical salaried earnings for similar people: about ₹15,491".
- *Category:* METHOD/BUG (under-fitting plus wrong training population), and PRESENTATION (the estimate is described as "typical").
- *Affects:* correctness, scientific validity, presentation, and ranking (it feeds `ml_rank` via the per-record maximum).
- *Demo:* **Yes.** At minimum, stop presenting the estimate as a "typical value" until the model is retrained on applicable persons only, with enough iterations.

**C2 — The brief's central requirement (historical / related-survey validation) is not implemented.** See §2.3. *Category:* SCOPE. *Demo:* the demonstration must say so explicitly.

**C3 — There is no evaluation of detection performance.** No error injection, labelled cases or E0–E7 execution. Therefore nobody can currently say whether the ranking finds errors better than chance, or better than the CAPI rules. *Category:* SCOPE/research. *Demo:* state it plainly. The Technical reference does say this.

### HIGH

**H1 — Priority bands and the "99% receive a priority" figure are artefacts of the formula, not evidence.**
- *Location:* `fusion/engine.py:260-271`, `fusion/config.py` (bands 0.8 / 0.5 / 0.2 / 0).
- *Evidence:* for two independent uniform ranks, P(U·V ≥ c) = 1 − c + c·ln c. That predicts 2.15% / 13.2% / 32.5% / 52.2% for CRITICAL / HIGH / MEDIUM / LOW. Observed: **2.09% / 19.7% / 16.2% / 61.0%**. CRITICAL matches the formula. The lower bands are reshaped by the zero-influence tie (H2/M4) and by source dependence.
  - Every record with *any* statistical target gets a priority. The statistical layer counts structural zeros as assessable: 88.8% of salaried and 83.2% of self-employed values are 0, and 63% of hours values are 0. So 99% coverage follows from the definition.
  - 266,475 records (**64.8%**) have raw influence = 0 and share one tied influence rank of 0.324. Their priority is capped at 0.324 × risk, so they can never be HIGH.
- *Category:* consequence of the definition of "priority" (a total ordering) plus percentile calibration. It is not a thresholding bug. A band says where a record sits in the ordering; it is not evidence that the record has an error. A defensible cut-off needs research (review capacity, outcome data).
- *Affects:* scientific validity, presentation. *Demo:* keep the disclosure (the UI does this). Do not describe bands as levels of concern.

**H2 — The influence quantity `weight × max |observed − peer median|` mixes rupees and hours and is methodologically inappropriate as an "impact" measure.**
- *Location:* `fusion/engine.py:142-143`, `fusion/influence.py`.
- *Evidence:* the maximum is taken across targets in different units. For anyone with an earnings target, a ₹21 deviation outranks the maximum possible hours deviation of 20. Hours-led cases can therefore only reach high influence through their weight. CRITICAL-band composition: salaried 4,282, self-employed 1,948, hours 2,449.
  - The design weight is the raw `MULT`, not the documented final weight. The READMEs specify MULT/100 or MULT/200 depending on NSS = NSC (and ÷ NO_QTR for annual or calendar-year estimates). Rank calibration removes the constant factor, but relative weights are wrong where the divisor differs: about 0.15% of 2023–24 records (NSS = NSC for 619 of 418,159; NO_QTR = 3 for 110).
- *Classification:* **methodologically inappropriate** as a measure of effect on estimates. As an engineering proxy it is **usable only within a single target** (e.g. weight × |deviation| for earnings alone). Across targets it is ill-defined, because the maximum of quantities in different units has no meaning. A defensible replacement would be a per-target, scale-free deviation, or an estimator-specific influence for a named indicator (e.g. the contribution to a weighted mean earnings estimate).
- *Category:* METHOD. *Affects:* ranking, scientific validity. *Demo:* the Technical reference already discloses mixed units. Supervisors should not be told this measures "effect on survey totals" without that caveat.

**H3 — FSU (group) evidence is propagated into individual record risk and can override it.**
- *Location:* `fusion/engine.py:241` (each person inherits the FSU's maximum pattern rank) and `:264-266` (override).
- *Evidence:* the override applied to 6,587 records. For **1,974** of them the only source at or above 0.995 was the FSU pattern; **427** of those are CRITICAL. This contradicts the project's own `pattern/DESIGN.md`: "group membership is not evidence that an individual record is anomalous".
- *Category:* METHOD. *Affects:* ranking validity. *Demo:* fix before any operational use; disclose for a demonstration.

**H4 — Stored digit-heaping statements frequently state the wrong direction.**
- *Location:* `pattern/engine.py:310-311`. The "dominant digit" is the FSU's most common digit. The statement "higher concentration … than the comparable reference population" is generated without comparing it with the reference.
- *Evidence (2024):* the statement is false (FSU share ≤ reference share) for **55%** of salaried-earnings rows, **70%** of self-employed, **48%** of hours and 2.6% of age rows. Among rows ranked ≥ 0.95 it is false for 58% (salaried), 23% (self-employed) and 46% (hours).
- *Category:* **BUG** in a stored evidence artefact. The case page avoids repeating it: it shows neutral titles plus both percentages, and the queue rewrites it to "differ". The wrong sentence is still stored, still in the technical JSON, and still appears in `pattern_statement`. *Demo:* the UI is mitigated; fix the backend.

**H5 — The earnings and hours Pattern checks mostly measure population composition (share of non-workers), not heaping or concentration.**
- *Location:* `pattern/engine.py` (`_heaping`, `_concentration`, `_distribution`). All persons are included, so structural zeros count as values.
- *Evidence:* the digit-0 share for earnings is essentially the share of non-earners. The FSU interquartile range of salaried earnings is 0 in **10,971 of 12,716** FSUs. 23,822 numerical distribution rows are not assessable for zero reference spread.
- *Category:* METHOD (applicability not handled). *Affects:* Pattern validity, and through H3, record ranking.

**H6 — Pattern scores are biased toward small FSUs.**
- *Evidence:* Jensen–Shannon distance has an upward small-sample bias. Spearman(n, rank) is **−0.47** for age heaping and **−0.42** for the industry mix; the mean rank falls from 0.67 in the smallest quartile to 0.33 in the largest (age heaping). There is no size adjustment (expected-JS baseline, permutation or bootstrap).
- *Category:* METHOD. *Affects:* false positives concentrated in small FSUs.

**H7 — LOF breaks down on tied, discrete data.**
- *Location:* `ml/lof.py`.
- *Evidence:* the median raw LOF is 1.0, but the 99th percentile is 2.3×10⁸ and **14,087** records score above 10⁶. This happens when local reachability densities collapse under duplicate points (identical hours and earnings). Ranks in the top tail are ordered by numerical degeneracy, not by meaningful local density.
- *Category:* METHOD (feature space unsuited to LOF without de-duplication or jitter-free handling). *Affects:* `ml_rank`.

**H8 — The current PLFS design (2025) is absent from the supervisor tool.** No 2025 Pattern or Fusion run exists, although 2025 statistical, contextual and ML runs do. *Category:* SCOPE.

**H9 — Not general-purpose, and integrity rules cannot be defined.** See O1 and F3. *Category:* SCOPE.

**H10 — There is no real-time or API ingestion.** See F1. *Category:* SCOPE.

### MEDIUM

**M1 — BUG: the concentration "mid-rank" counts ties 1.5×.**
- *Location:* `pattern/engine.py:288`. `(le(spread) + 0.5·eq(spread)) / n` should be `(lt + 0.5·eq) / n`.
- *Evidence:* **22,795 of 50,864** positions exceed 1, and evidence scores go negative (minimum −0.5). Low-variance FSUs that tie with peers are under-ranked.

**M2 — Concentration reference spreads include FSUs below the minimum size.** Small FSUs have mechanically small IQRs. The reference rows are not filtered to n ≥ 10. *Category:* METHOD.

**M3 — Contextual surprisal is not comparable across reference sizes.** A code held by this person alone scores surprisal 3.95 (reference < 100), 5.32 (100–499) or 6.84 (500+). It is then globally percentile-ranked, so the same evidence ("unique in its group") ranks very differently by group size. Rarity is also not error: 9.2% of assessable codes are below 1% conditional frequency. *Category:* METHOD/LIMITATION.

**M4 — Statistical "assessable" includes structural zeros, and "no deviation" is not rank 0.** The 99% coverage is overstated; the meaningful populations are about 46k salaried earners, 69k self-employed and 152k persons with non-zero hours. A record with no deviation on any target gets a statistical rank of about 0.3 (the mid-rank of the large zero tie), not 0. `fusion/DESIGN.md` says only an *all*-zero source becomes 0. *Category:* METHOD/LIMITATION.

**M5 — Risk depends on how many sources are available.** Mean risk is **0.37** with 3 sources and **0.66** with 4. Contextual evidence exists only for workers with an occupation code, so risk is largely a "worker" indicator. Records with a single source sit at the extremes; averaging ranks regresses multi-source records toward 0.5. *Category:* METHOD.

**M6 — Dependent sources are counted as complementary evidence.** Earnings drive the statistical layer, conditional ML (C1), Isolation Forest, LOF and influence. The UI correctly says the sources are "not independent proofs", but the weighted mean still adds the same signal several times. *Category:* METHOD/LIMITATION.

**M7 — Isolation Forest mainly ranks rare category combinations.** It uses 25 trees, one-hot categoricals, and median imputation of non-applicable earnings plus indicators. The top 1% is 99.8% workers, and rare activity statuses make up 25% vs 4% elsewhere. It is weak but usable as a "rare combination" signal; 25 trees give a noisy ranking. *Category:* LIMITATION.

**M8 — Documentation disagrees with the code.** `ml/DESIGN.md` says the conditional model is "bounded to 100,000 stable reference records per fold"; the code uses `maximum_training_rows = 50_000`. The ML design also does not mention that the model trains on structural zeros. *Category:* engineering quality.

**M9 — PRESENTATION: the FSU headline sentence appears on almost every case.** `explain._reasons` adds "belongs to an FSU whose overall response pattern differs" when *any* one of about 12 FSU checks has rank ≥ 0.8. **88.8%** of persons (91.8% of the top 1,000) qualify. For 38.8% of them the fused pattern rank is below 0.5. Case #8 (fused pattern rank 0.126) carries the sentence while its own FSU card says "Not notably unusual".

**M10 — PRESENTATION: "far above / far below typical" is used for anything outside the 5th–95th percentile.** By construction, about 10% of each peer group's non-zero values receive this wording. "Above the usual range" would be accurate.

**M11 — PRESENTATION: the salaried-earnings model section is shown for people with no salaried work** ("salaried earnings ₹0 … estimated about ₹0").

**M12 — Weight formula not applied.** See H2.

**M13 — Export truncates at 10,000 rows without telling the user.** `fusion/api.py:323`. CSV only.

**M14 — Security.** See N2. Acceptable for a local prototype; not compliant for deployment.

**M15 — Seasonality is handled inconsistently.** Pre-2025 peer groups pool all four quarters (no quarter boundary). Post-2025 groups are split by month. Seasonal hours and earnings in agriculture are therefore pooled across a year for 2023–24 and 2024, but not for 2025.

### LOW

- **L1** — LOF with `novelty=True` scores its own training points (self-neighbour). The measured effect is small: 3.3% vs 3.7% in the top 5% within large groups.
- **L2** — Exact-signature matches: 67% are children under 15 and 86% have status 91/99. These are correctly excluded from priority and labelled "for information". The stored statement says "highly similar" although only exact matches exist.
- **L3** — Percentiles, medians and MAD are unweighted: they describe the sample, not the population. This is defensible for validation but should be stated.
- **L4** — Percentile, median and MAD include the observation itself. Masking is negligible for n ≥ 30.
- **L5** — The cross-fitting folds are not grouped by household or FSU, so there is minor leakage through household-level similarity.
- **L6** — Stale or partial run directories without `run_metadata.json` (`pattern/runs/2023_24_first_visit_2023_24_first_v1`, `…_pattern_v1`).
- **L7** — `contextual/engine.py:383-385` reads the assignment and reference tables twice (performance only).

### OBSERVATIONS (strengths, evidence-based)

- Strict provenance gating at every layer (release, observation, design period and preparation run ID must match), immutable run directories, deterministic IDs. ML reproducibility was verified by an independent re-run.
- Structural-break discipline: no pooling across the January 2025 redesign or across months for 2025.
- An append-only review audit stores an evidence snapshot with each decision.
- Careful language: "unusual ≠ incorrect", FSU ≠ enumerator, sources described as not independent, the 99% disclosure, known limitations listed on the Technical reference page.
- 56 automated tests pass. They establish software behaviour only.

## 4. Layer-by-layer methodology notes

### 4.1 Preprocessing
Deterministic and traceable, with no imputation and blanks and zeros counted separately (good). NIC codes keep their leading zeros in all three releases (verified: 5 characters, `01111`…`97009`), so 2-digit division coarsening is correct. Missing: applicability masks. Because of that, structural zeros in earnings flow downstream as real values. This is the root cause behind C1, H5, M4 and part of H1.

### 4.2 Peer groups
Reasonable backoff hierarchy, minimum 30, FSU and weight excluded. Backoff is heavy: 72–78% of assessable target rows use a backoff level, mostly non-workers without occupation or industry. The quarter is not a boundary before 2025 (M15).

### 4.3 Statistical
The robust median/MAD modified z-score (0.6745 constant), mid-rank percentiles and zero-MAD handling are correctly implemented and documented. "Unusual" = outside 5–95%, so about 10% of non-zero values per group are tails by construction. That is fine as a description, not as a flag rate. Zero-MAD affects 89% of salaried rows (structural zeros).

### 4.4 Contextual
The conditional frequency of the 3-digit NCO code within the day-7-hours peer group (state × sector × CWS status × NIC division). There is no target leakage: occupation is not in the reference. Rarity is measured correctly, but it is size-dependent (M3) and not error. Principal-status occupation is conditioned on *current-week* status; that is defensible, but should be stated.

### 4.5 ML
- **Isolation Forest:** see M7.
- **LOF:** H7 and L1. The documentation matches the code.
- **Conditional model:** C1 and M8. Cross-fitting prevents self-leakage (good).
- **Exact signature:** L2.

No component uses state or sector as a feature (the conditional model omits geography), which contributes to the state-level residual pattern in C1.

### 4.6 Pattern
H4, H5, H6 and M1/M2. Temporal drift is non-functional on first-visit data (§2.3). The revisit-transition component was not used in the fused 2023–24 run. Leave-FSU-out references are correctly constructed.

### 4.7 Fusion
- Percentile calibration is correctly implemented, but it converts every source to "rank among this round". It removes magnitude, so a merely mild case at the 99th rank looks like an extreme one.
- Unavailable sources are excluded (good), but that creates the source-count dependence (M5).
- The override threshold of 0.995 combined with FSU inheritance gives H3.
- Influence: H2.
- Bands: H1.

### 4.8 Explanation / UI
Faithful to the stored outputs in nearly all statements, with jargon hidden behind Technical details, a clear record-vs-FSU distinction, comparison groups and backoff disclosed, and "estimate is a guide, not a correct value" stated. Issues: C1 (estimate presented as typical), M9, M10, M11. "Combined evidence stronger than about 99.9% of records" is shown even when the override made risk equal one source's rank.

## 5. What should be fixed before a demonstration

1. **C1:** stop presenting the conditional-model estimate as the "typical value", or retrain it on applicable persons with adequate iterations.
2. **H3:** remove FSU evidence from record-level override (or from record risk), or show clearly when a record's position comes from group evidence.
3. **H4 and M1:** fix the heaping statement direction and the concentration mid-rank.
4. **M9:** show the FSU sentence only when the fused FSU rank is itself notable.
5. Say explicitly, in the demonstration, that historical / cross-round validation, temporal drift, aggregate-level checks, real-time ingestion, user-defined rules and performance evaluation are **not yet implemented**.

## 6. Overall verdict

| Dimension | Assessment |
|---|---|
| Problem-statement compliance | **Partial — core requirement (historical/related data, temporal drift, aggregate level, real-time, rule definition, evaluation) unmet.** |
| Scientific / methodological correctness | **Mixed.** The statistical and contextual layers are sound as descriptions. ML has one invalid component (C1) and one degenerate one (H7). Pattern has applicability and size-bias problems. The Fusion formulation is not yet defensible as a measure of anything beyond an ordering. |
| Algorithm correctness | Two bugs (H4, M1). One mis-specified model (C1). |
| Implementation correctness | Generally high: provenance, determinism, memory-bounded streaming. |
| Data / survey-design correctness | Good boundary discipline. Weight formula not applied (H2). Applicability of zeros not handled. Seasonality inconsistent (M15). |
| Evaluation validity | **None yet** (C3). |
| Result validity | Rankings are dominated by earners with high values. Group evidence leaks into record ranks. Bands are formula artefacts. |
| Explainability | **Strong**, with the four presentation issues listed. |
| Scalability / engineering | Good for batch at PLFS scale (2025: 1.15 M rows). No ingestion service or auth. |
| UI / workflow | Correct human-in-the-loop workflow. Layout defect (unused right-hand space) fixed separately. |

The current implementation is a credible, carefully engineered **foundation**. It does not yet demonstrate that it detects survey errors, and it does not use past data, so it does not yet address the brief's stated problem. The honest framing for HSD is: *"a provenance-safe evidence and review workbench for within-round outlier screening, with historical, temporal, aggregate and evaluation capabilities still to be built."*
